# 主动触发机制设计（对标 Muse）

## Muse 是怎么做的（据官方复盘，2026-09）

三个要点，来源：[Meta 复盘 Muse：Agent 怎么才能像「一个人」长期存在？](https://hub-assets-cache.baai.ac.cn/view/58273)

1. **事件驱动，不是 cron**：目标设定后「按照日程安排、或在相关事件发生时继续推进」。案例（体育选拔 12 小时截止）来自它盯邮件时从内容中发现，不是整点巡检。
2. **唤醒与打扰分离**：后台工作完成后「先判断结果值不值得告诉你，只有有意义的新进展或需要用户参与时才通知」。心跳可以有固定频率，开口必须过判断门。
3. **门槛高且用户可调**：「主动发消息的门槛必须很高」；用户可关掉/调低/调高频次。「分寸感」被当作专门训练的能力。

另有第三种主动性：Ideas——持续根据目标、行为模式、对话信息生成「你能让我做什么」的建议（提示 / 想法标签页 / 主动分享）。

## 刻板感的真正来源

固定 30 分钟不刻板；**每次醒来都必定开口**才刻板。噪音 = 触发频率 × 说话率。Muse 的解法是压低说话率（判断门），而非消灭心跳。

## dsh-muse 的三层去刻板化

| 层 | 机制 | 状态 |
|---|---|---|
| 1. 静默心跳 | 定时唤醒 + 「检查但未必说」语义：无值得说的事就只记日志、保持沉默 | ✅ 已用于演示脉冲（schedule-3b61f067，2 小时静默心跳） |
| 2. 事件源 ingress | 文件变动 / webhook / 收件触发唤醒，「有事才醒」替代「到点就醒」 | ⏳ 未建（gaps.md 第 2 层） |
| 3. 值得打扰判断门 + 用户可调频次 | 唤醒后的结构化判断（窄判断即可）；设置里开放 关闭/低频/高频 | ⏳ 未建（gaps.md 第 5 层） |

## 静默的边界（实测修正）

prompt 层的「静默」只能压低打扰度（不展开、内容最短），**不能消除痕迹**：静默检查本身是一个 turn，GUI 必然出现任务卡片。要「无痕静默」，判断门必须下沉到对话外——宿主侧代码在投递前预检（如脚本查信号文件），没事就不创建 turn。这属于 gaps 第 5 层的代码化实现，配套事件源 ingress。

在那一层建好之前，可达的上限是「留痕但不打断」；且按 Muse 的透明度原则（「看不见的东西，很难让人信任」，活动记录是刻意设计），留痕本身是特性而非缺陷。

## 演示验证中的一个真实发现

定时投递**需要会话空闲**：agent 忙碌（目标自动续跑轮次占用会话）时提醒被压住，空闲后补投。这意味着心跳语义必须考虑「醒来时可能已迟到 N 个周期」——投递侧是 at-least-once + 补投，不是精确时刻。与 Muse「永远在线的云端电脑」的差异再次指向冷唤醒/守护化（gaps.md 第 1、3 层）。
