# B06 · 单会话多目标（Muse 核心体验的最后一里）

- 状态：deferred（依赖上游 DSH 能力；解除条件见下）
- 来源：用户指出「多会话多目标」违背 Muse「一个对话装下所有事」的核心体验

## 问题定义

Muse：一个主对话，多个并发目标（各有进度/节奏/预算），单一 agent 交错处理。
DSH 现状：`create_goal` 单会话单目标；goal-round-driver 围绕单目标设计。

## 已验证的近似与它们的不足

| 方案 | 体验差距 |
|---|---|
| 多会话各挂一个目标 | 违背单一对话核心体验（用户明确否决） |
| 顺序目标（完成一个开下一个） | 无并发感，新目标要等旧的完成或替换 |
| muse_routine 多任务池 | 已支持多任务轮转，但 routine 是「定时工作单元」不是「长期目标意图」——缺少目标级的进度追踪与完成语义 |

## 解除条件（deferred → ready）

上游 DSH 的 goal 工具支持单会话多目标（goal 列表 + 独立 round-driver 实例），或
DSH 提供 goal-queue 原语（目标队列 + 顺序/优先级推进）。

出现任一能力后，本仓库的工作是薄的适配层：多目标的 routine 节奏绑定 + 聚合视图（muse-dashboard 已有雏形）。

## 过渡期方案（体验近似，已可用）

单会话内：1 个 flagman goal（推进主干）+ muse_routine 多任务（并行常驻承诺）+ reflect 想法池。
这与 Muse 的真实形态接近：单一 agent、交错注意力的多承诺，而非真并行。

## 上游反馈价值

这是对 DSH goal 子系统的真实产品需求（来自 Muse 对标实践），值得作为 feature request 反馈上游：
「单会话多目标：goal 列表 + 独立轮次预算 + 聚合视图」。
